# Этап 4. Views — Implementation Plan

> **Для исполнителя:** реализовывать задача за задачей, по TDD. Шаги отмечены чекбоксами (`- [ ]`).

**Goal:** сохраняемые срезы задач — фильтры по грамматике §4 модели данных, сортировка,
группировка и layout, — с правами трёх scope и выполнением `GET /views/{id}/tasks`.

**Architecture:** модуль `views` (пятислойный) плюс два чистых слоя:
`views/filters.py` — Pydantic-грамматика фильтров, разрешение динамических значений и
трансляция в условия SQLAlchemy по белому списку; `tasks/ordering.py` — сортировка с курсором и
выражения группировки. Выполнение view — `TaskService.run_query`: только репозиторий задач
ходит в таблицу задач, а view передаёт ему готовые условия.

**Spec:** `…-roadmap.md` («Этап 4»), `…-data-model.md` (§4), `…-vision.md` (сценарий В),
`…-cli-spec.md` (§5 view), `…-mcp-spec.md` (`list_views`, `run_view`).

## Решения сверх спеки (внести в спеки в последней задаче)

1. **Ответ выполнения всегда сгруппирован:** `{"group_by", "groups": [{"key", "count", "items",
   "next_cursor", "has_more"}]}`. Без группировки — одна группа с `key = null`. Страница — на
   группу: `?group=<key>&cursor=` листает одну колонку доски; `group=none` — группа без значения.
2. **Группы — только непустые.** Порядок групп: `priority` — 1, 2, 3, 4, затем 0 (без
   приоритета); `state` — по типу (backlog → canceled), затем `position`; `assignee`, `project`,
   `label` — по имени; `due_date` — по дате. Группа «без значения» — последней.
3. **Задача с несколькими метками** попадает в группу каждой метки; `count` считает задачи.
4. **Командный view неявно ограничен своей командой** (`team_id = view.team_id`).
5. **Права.** Личный view создаёт любой участник workspace, включая гостя: выполнится он всё
   равно в пределах видимых гостю задач. Командный — участник команды с эффективной ролью
   `member`. Workspace — `admin`. Видят: личный — владелец; командный — участники команды;
   workspace — все, кроме гостей. Менять и удалять: личный — владелец; командный — автор или
   эффективный `admin` команды (лид, admin workspace); workspace — автор или `admin`. Невидимый
   view — `404 view_not_found`, видимый без права изменения — `403 insufficient_role`.
6. **Scope, команда и владелец view не меняются** после создания.
7. **Семантика операторов.** `nin` для необязательных полей (`project_id`, `assignee_id`)
   включает пустое значение: «исполнитель не я» включает задачи без исполнителя. Даты
   сравниваются по UTC-дню: `lte @today` для `created_at` — «создано до конца сегодняшнего дня».
   `title contains` — `ILIKE` с экранированием `%`, `_`, `\`. `is_blocked` — есть незакрытая и
   неудалённая задача, которая блокирует эту.
8. **`@me`** допустим только в `assignee_id` и `creator_id`; `@start_of_week` — понедельник.
9. **Сортировка `priority`** ставит «без приоритета» после «низкого»; `due_date` — пустые
   всегда последними, в обе стороны. Тай-брейк — `id`.
10. **Курсор** несёт поле сортировки: сменили сортировку view между страницами —
    `400 invalid_cursor`.

Добавлено по ходу реализации:

11. **Запрошенная пустая группа** (`?group=1`, а задач с таким приоритетом нет) приходит с
    `count = 0` и пустым списком — колонке доски так проще, чем гадать по пропаже группы.
12. **Сравнения `priority`** (`lt`…`gte`) идут только среди назначенных приоритетов (`> 0`):
    пример спеки `priority lte 2` — «срочные и высокие», без задач без приоритета.
13. **`ViewRead.can_edit`** — интерфейсу не нужно повторять правила прав, чтобы скрыть кнопки.
