# Этап 8. MCP-сервер — Implementation Plan

> **Для исполнителя:** реализовывать задача за задачей, по TDD. Шаги отмечены чекбоксами (`- [ ]`).

**Goal:** `tkl-mcp` — MCP-сервер поверх `taskanline_sdk`: инструменты чтения и записи, ресурсы,
промпты, транспорты stdio и streamable HTTP. Готово, когда проходит сценарий Д: модель отвечает
«что сейчас в работе у команды ENG» и создаёт задачу; при `--read-only` инструмента записи нет.

**Architecture:** пакет `taskanline_mcp`: `server.py` строит `MCPServer` (Python SDK `mcp` 2.x,
бывший FastMCP) из `ServerSettings`; каждый вызов инструмента открывает клиент SDK с токеном
процесса (stdio) или из заголовка `Authorization` (HTTP) и `Resolver` для имён. `present.py` —
компактный вид объектов, `errors.py` — исключения SDK в текст с подсказкой. Своих HTTP-вызовов
и обращений к базе нет.

**Spec:** `…-mcp-spec.md` (весь), `…-roadmap.md` («Этап 8»), `…-vision.md` (сценарий Д).

## Решения сверх спеки (внести в спеки в последней задаче)

1. **`mcp` 2.x:** FastMCP переименован в `MCPServer` (`mcp.server.mcpserver`); сигнатуры сверены
   с установленной версией 2.3.
2. **Разрешение имён — в SDK** (`taskanline_sdk.resolve.Resolver`), общее с CLI: ключи команд,
   статусы, метки, email, ключи задач, имена views.
3. **HTTP-режим берёт токен только из заголовка**, токен процесса там не используется: иначе
   любой, кто достучался до порта, работал бы с правами владельца процесса.
4. **Конфиг CLI читается своим маленьким модулем**, а не импортом `taskanline_cli`: архитектура
   запрещает SDK читать конфиги, а тянуть Typer и rich в MCP-сервер ради чтения TOML незачем.
5. **Очистка поля в `update_task` — списком `clear`**, а не явным `null`: схема инструмента не
   отличает «не передано» от `null`, а модель от `clear: ["due_date"]` не ошибётся.
6. **Ошибки инструментов — `CallToolResult(is_error=True)` с текстом**, без префикса фреймворка
   «Error executing tool …».
7. **`list_views`** излагает фильтры словами с именами вместо id.
