# Этап 3. Ядро задач — Implementation Plan

> **Для исполнителя:** реализовывать задача за задачей, по TDD. Шаги отмечены чекбоксами (`- [ ]`).

**Goal:** задачи с ключами `ENG-142`, настраиваемые статусы команды, ручная сортировка дробным
индексом, подзадачи, связи с детектором циклов, метки, комментарии с @упоминаниями, история
изменений, уведомления и идемпотентное создание задач.

**Architecture:** шесть новых модулей по обычной пятислойной схеме — `states`, `tasks`, `labels`,
`comments`, `activities`, `notifications` — и служебный `idempotency`. Две чистые функции в `core`:
`fractional_index.py` (ключи `sort_order`) и `pagination.py` (курсор). `core/permissions.py`
учится находить объект по задаче, статусу, метке и комментарию тем же одним запросом с тремя
`LEFT JOIN`, и получает SQL-предикат видимости задач для списков.

**Tech Stack:** FastAPI, SQLAlchemy 2.0 async, Alembic, PostgreSQL 16.

**Spec:** `…-roadmap.md` («Этап 3»), `…-data-model.md` (§3 целиком, §5 `idempotency_keys`, §6.3
Task, §7), `…-architecture.md` (§3.2, §3.5, §3.6, §3.8), `…-cli-spec.md` (§5 task, §7),
`…-mcp-spec.md` (§4).

## Context

Этапы 0–2 закрыты: есть пользователи, `Principal`, организационная структура и слой прав. Этап 3 —
главный функционал продукта. Веб-клиент не трогаем: экраны задач — этап 5, и roadmap прямо
предостерегает писать интерфейс под неустоявшуюся схему. Единственная правка во фронтенде —
перегенерированный `schema.d.ts`, иначе джоба CI `api-types` упадёт на расхождении.

**Решения сверх спеки** (внести в спеки в задаче 16, тем же изменением):

1. **`sort_order COLLATE "C"`.** Алфавит base62 (`0-9A-Za-z`) упорядочен по ASCII, а
   лингвистическая сортировка `en_US.UTF-8` ставит `a` перед `B`. Без побайтового сравнения
   порядок в базе разошёлся бы с порядком, который считает функция генерации.
2. **Порядок общий на команду.** `sort_order` сравнивается внутри команды, а не внутри колонки
   статуса. «После X» — это между X и его соседом по всей команде; тогда задача встаёт сразу
   после X в любом срезе — доске, списке проекта, view. Новая задача встаёт в конец команды.
3. **`move` принимает якорь, а не ключ.** `{state_id?, after_id? | before_id? | position: top|bottom}`
   — сервер сам находит соседа. Совпавшие ключи соседей (гонка двух перестановок) или ключ
   длиннее 32 символов запускают перегенерацию всей команды под блокировкой строки команды.
4. **Ключ задачи в пути и ссылках тела.** `{task_id}` в пути и поля-ссылки на задачу в теле
   (`parent_id`, `target_id`, `after_id`, `before_id`) принимают и UUID, и `ENG-142` в любом
   регистре. Ключ уникален внутри workspace, а не глобально: если он нашёлся в нескольких
   видимых пользователю пространствах, ответ — `409 task_key_ambiguous` со списком
   `details.workspace_ids`; уточнение — `?workspace_id=`.
5. **Доступ к задаче** — роль на её проекте, если проект есть, иначе на команде. Создание задачи
   в проекте проверяется на проекте: участник проекта без членства в команде (подрядчик) может
   заводить задачи в своём проекте.
6. **Новые типы `activities`:** `title_changed`, `description_changed`, `project_changed`,
   `parent_changed` — иначе изменения этих полей не оставляли бы следа. `description_changed`
   не хранит текст: описание бывает большим, а история append-only.
7. **Связь пишется в историю обеих задач** — с типом, прочитанным со стороны каждой
   (`blocks` у источника, `blocked_by` у цели).
8. **Связь `relates_to` симметрична:** `A relates_to B` и `B relates_to A` — одна связь, вторая
   получает `409 relation_exists`. `blocked_by` и `duplicated_by` хранятся перевёрнутыми.
9. **Подзадача может лежать в другой команде** того же workspace, но родитель обязан быть виден
   актору. Глубина — не больше пяти уровней, считая корень.
10. **Упоминание — `@email`** (как в MCP-спеке). Упомянутый без доступа к задаче не
    материализуется и уведомления не получает: уведомление раскрыло бы задачу.
11. **Метки уровня workspace** создаёт и меняет `member` workspace (как метки команды — `member`
    команды); гостю недоступно. Список `GET /labels?workspace_id=` отдаёт метки workspace и
    видимых команд; с `team_id` — метки этой команды и метки workspace.
12. **Комментарий:** изменить — только автор; удалить — автор или `admin`. Под токеном со
    `scope = read` оба действия — `403 insufficient_scope`.
13. **Удалённая задача** отвечает `404 task_not_found` везде, кроме `restore`; список отдаёт
    удалённые только по `?deleted=true`.
14. **Удаление статуса:** статус по умолчанию удалить нельзя (`400 state_is_default`); статус с
    задачами — только с `?move_to=` (иначе `409 state_has_tasks`), перенос пишется в историю
    каждой задачи и пересчитывает `started_at`/`completed_at`.
15. **Миграция `0003` досоздаёт стандартные статусы** командам, заведённым до неё.
16. **Ответ повтора по `Idempotency-Key`** несёт заголовок `Idempotent-Replayed: true`.
    Хеш запроса — SHA-256 канонического JSON тела после валидации.
17. **Список задач требует `workspace_id`:** изоляция — свойство запроса. Фильтры — повторяемые
    query-параметры (`?state_type=started&state_type=unstarted`); `assignee_id` принимает `me`
    и `none`. Полнотекстовый `q` — `websearch_to_tsquery('simple', …)` по тому же выражению,
    что и индекс `idx_tasks_search`.
18. **`?expand=`**: `assignee`, `creator`, `state`, `labels`, `project`, `parent`; `relations` —
    только в детальном ответе. Неизвестное значение — `400 invalid_expand`. Без `expand` в
    ответе плоские id, включая `label_ids`.
19. **Приоритет в API — число 0–4**, как в базе. Имена (`urgent`, `high`, …) — забота SDK/CLI.
20. **Комментарии** отдаются по возрастанию времени, **история** — от новых к старым; обе с
    курсором.

## Global Constraints

- Комментарии, докстроки, коммиты — на русском; имена — на английском.
- Ветка `feat/tasks` от `dev`. В `dev`/`main` не вливать и не пушить.
- Слои модуля; сервис не трогает чужой репозиторий; циклические зависимости сервисов —
  импортом внутри функции.
- Ошибки — `ApiError`. Нет доступа → 404, 403 — только видимому объекту.
- Мутация под `scope = read` → `403 insufficient_scope`.
- Enum'ы — `VARCHAR` + `CHECK` и `StrEnum` в `core/enums.py`. PK — UUIDv7. `updated_at` пишет
  приложение.
- Миграции ровно `0003_tasks` и `0004_collab` с рабочим `downgrade`.
- Запись в `activities` — в той же транзакции, что и изменение, с `actor_token_id`.
- Новое действие в матрице — строка в `Permission`, запись в `MIN_ROLE`, кейс в
  `test_permission_matrix.py`.

## Review Focus

1. **Видимость в списках совпадает с `compute_effective_role`.** Предикат SQL и чистая функция —
   две реализации одного правила. Тест сверяет их на всех формах членства.
2. **Гонка выдачи номеров.** `UPDATE teams … RETURNING` сериализует создание в команде; номера
   без дыр и без повторов.
3. **Коллация `sort_order`.** Тест сравнивает порядок базы с порядком Python на ключах разного
   регистра.
4. **Цикл через `blocked_by`.** Перевёрнутая связь участвует в обходе так же, как прямая.
5. **Утечка через ключ.** Ключ задачи из приватной команды не находится и не попадает в
   `task_key_ambiguous`.
6. **Пагинация при вставках.** Вставка перед курсором не даёт ни дублей, ни пропусков.
